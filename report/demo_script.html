1 · The problem and the user

Bhavani0:00–0:45
On screen
  • Slide 1 — title, the sample message, and the number 77.
Say

"Good evening. We are Group 22, and our project is SafeBank Assist."

"A retail bank's support desk gets thousands of short, messy messages a day. Something like this one — 'My new card still hasn't arrived and it's been two weeks.' For every message, a first-line agent has to work out what the customer actually wants, out of 77 possible request types in the BANKING77 dataset, decide whether a system lookup is needed, and reply without inventing anything about the customer's account."

"Done by hand it is slow, and two agents answer the same message differently. The hardest cases are near-twins: 'my card hasn't arrived' and 'when will my card arrive' are two different intents, and they route to different places."

"Our target user is the tier-1 support agent, and through a self-service channel, the customer behind them."

2 · What we built, and why a generative model

Bhavani0:45–1:30
On screen
  • Slide 2 — the JSON output shape: intent, confidence, reply, tool call, escalation flag.
Say

"SafeBank Assist reads one message and returns one validated decision: the BANKING77 intent, a confidence value, a reply the customer can safely read, an optional call to a banking tool, and a flag to hand over to a human."

"Why a generative model and not a classifier? A classifier gives us the label and nothing else — no reply, no routing decision. A pretrained instruction-tuned causal LM gives all three in a single prompted pass, and adding a new request type is a prompt edit instead of a retraining run. We compared it against GANs, VAEs and diffusion models in section 4.1 of the report: those generate continuous data and are conditioned differently; text is discrete and autoregressive, so a causal LM is the right family here."

"The catch is that the model's output is just text. So most of what we built is the machinery that checks that text before anyone acts on it — and that is what the rest of this demo shows."

Say

"This is the real tokenizer output for one evaluation message. 'I need to activate my card can you do that now?' — 47 characters becomes 12 tokens, each about four characters. Byte-level BPE, so a misspelt word never fails as out-of-vocabulary; it just becomes more pieces."

"The same cell reports the checkpoint we actually loaded: vocabulary 151,643, hidden size 1,536, 28 decoder blocks, 12 attention heads, context 32,768. Each token's embedding goes through masked self-attention and feed-forward layers, and the language-modelling head turns the last hidden state into one probability per vocabulary entry — that is the next token. Generation is that step, repeated."

"Here is our baseline, E1: one deliberately plain prompt, no intent list, no schema, greedy decoding, GPT-2 against Qwen on the same five messages. GPT-2 never answers the question — it continues the text pattern, repeats the prompt back, and on the ATM message gets stuck repeating one phrase. That is what a model with no instruction tuning does. Qwen gives a correct one-sentence summary for all five — but none of its replies is one of the 77 labels, and nothing in the output can be validated or routed."

"So the baseline tells us the instruction-tuned model understands the request, and that understanding alone is not a system."

5 · The pipeline: the model proposes, code decides

Kishore3:00–3:45
On screen
  • Slide 5 — the pipeline arrows. Report §5 has the same diagram if anyone wants it bigger.
Say

"The workflow is: message, into a programmatic prompt template, into the tokenizer, into the model, decoding control, raw text out. Then the deterministic half: parse the JSON, validate it against a Pydantic schema, and if it fails, show the model its own rejected reply plus the validator's errors and ask again — at most twice."

"Then the label must exist in BANKING77 — an invented label is the clearest hallucination signal we have. Then a confidence gate, then the tool router, then a simulated tool, then a reply-safety screen, and finally the composed reply with a disclaimer, or an escalation with a stated reason."

"One design rule holds the whole thing together: the model proposes, deterministic code decides. The prompt is one reusable template — build_prompt(strategy, query, allowed_intents, **kwargs) — so all four prompt strategies you'll see next are the same pipeline with one argument changed. Nothing unvalidated reaches the customer, and a card is never blocked automatically."

7 · E2 — four prompt strategies

Satya5:00–6:00
On screen
  • Slide 7 — E2. Then notebook 2 at the E2 summary cell, or report §7's table.
Say

"E2 is the same pipeline run four times, changing only the prompt strategy: zero-shot, few-shot, role and context, and constraint-based. All four on the same 385 messages, greedy decoding, and all four render the label catalogue, the tool catalogue and the output contract through the same three functions — a test asserts those blocks are byte-identical, so any difference comes from the strategy, not from wording."

"Few-shot wins: 47.8% accuracy, macro-F1 0.450, against 40.3% zero-shot, 39.0% role/context and 40.0% constraint-based. Because the comparison is paired we could test it: few-shot was right on 55 messages where zero-shot was wrong, and wrong on 26 where zero-shot was right — exact McNemar, p equals 0.002. The other three cannot be told apart at all, p from 0.47 to 1.0, so their order in that table is not a ranking."

"Now the part we did not expect. Two of our four hypotheses were wrong. We expected few-shot to raise first-attempt validity by showing the format — it lowered it, from 95.1% to 83.4%. Every single one of those 53 failures was the model inventing a tool name outside our three-tool enum, things like check_transfer_status. Our worked examples all contain tool calls, so the model seems to have learned to attach one to everything. The enum caught all of them before the router saw them."

"And the role persona did not make replies safer — 19.0% asked for credentials against 17.4% for zero-shot, though it did hand over to a human more often."

8 · E3 — decoding study

Satya6:00–6:50
On screen
  • Slide 8 — E3, or report §8's table of six configurations.
Say

"E3 holds the model and the prompt fixed — few-shot, the E2 winner — and changes only how the next token is chosen. Six configurations: greedy, temperature 0.7 and 1.2, top-k 50, and top-p at 0.9 and 0.95, on a 77-message subset, one per intent. Each sampled configuration ran under five seeds, 42 to 46; greedy ran once because it is deterministic."

"Greedy was best at 48.1%. Sampling at 0.7 cost about three points, and at 1.2 it cost 8.6 — down to 39.5%, with final validity down to 84.4% and 37% of cases escalating. So sampling cost us accuracy and reliability and gained nothing we could measure. Our default stays greedy."

"Top-k 50 behaved exactly like plain temperature 0.7 — same accuracy, same agreement, at every seed. At temperature 0.7 almost no probability mass sits beyond the 50 most likely tokens, so the cut-off removes nothing."

"One methodological point worth naming: Qwen ships a generation config with sampling already on — temperature 0.7, top-k 20, top-p 0.8. Left alone, our 'temperature only' row would secretly have been temperature plus top-k plus top-p. We reset all of them, and top_k specifically has to be set to 0, because None gets refilled from the model's own config and puts 20 back. Without that fix every row in this table would have meant something other than its label."

"And stability is not correctness. At 0.7, 58% of messages get the same answer from all five seeds — but one message about setting up an account for a daughter gets the same wrong label from greedy and from almost every seed. Confidently and consistently wrong."

9 · E6 — evaluation and failure analysis

Satya6:50–7:35
On screen
  • Slide 9 — E6. Report §11 table and §12.1 failure table ready for questions.
Say

"We evaluate on six criteria, not one: intent accuracy and macro-F1; schema validity before and after repair; tool-routing correctness; reply safety; latency and attempts per reply; and self-consistency across seeds."

"Baseline zero-shot against the final few-shot system: accuracy 40.3% to 47.8%, unsafe replies 17.4% down to 3.9%, routing 62% to 68%, escalations 28.1% down to 21.0%, at a cost of 1.22 generations per message instead of 1.10."

"The repair loop raises few-shot validity from 83.4% to 94.8% — but the breakdown matters more than the headline. It rescued 47 of 60 formatting failures and only 1 of 62 invented labels. The reason is in our own prompt: the retry shows the model its rejected reply and the validator's errors, but it never re-states the valid label space, so a model that has invented a label has nothing new to choose from. Putting the catalogue into the repair prompt is the obvious fix, and we did not make it because it would invalidate every validity number in the report."

"For failure analysis we recorded six analysed cases across five classes and 15 safety findings. Routing is not an independent source of error — every one of the 16 misses and all five unnecessary tool runs followed a wrong intent. Routing is only as good as the label."

10 · The safety result, and the adaptation decision

Kishore7:35–8:15
On screen
  • Slide 10 — the safety numbers and the adaptation decision. Then slide 11 for the group close.
Say

"The result we care about most is not the accuracy. Zero-shot asked the customer for an account number, a card number or a secret in 65 of 385 replies — 16.9%. Few-shot cut that to 15, 3.9%. Nine of those 15 asked for an actual secret: a PIN, CVV or one-time code. All 15 were withheld and escalated."

"Every one of them was valid JSON with the correct intent. That is the whole argument for the deterministic layer: a reply can pass every structural check and still be unsafe, and no accuracy metric will tell you."

"On adaptation — we compared prompting, RAG and PEFT. RAG we rejected: there is no external corpus to retrieve, the whole catalogue fits in context, so it would add latency and a new failure mode for nothing. We chose prompting, and our own numbers argue against stopping there: 47.8% on a 77-way task is not production-ready, and we have 10,003 labelled training messages sitting unused. A LoRA adapter is the next thing we would do, and we say that in section 9 rather than defending prompting."

QuestionAnswerWho takes it
"Only 47.8%? Isn't that poor?"Yes — and we say so. It is a 77-way, fine-grained task with deliberately overlapping classes, no training, and a 1.5B model. The point of the project was the workflow and its controls, not a leaderboard number. The fix we identify is a LoRA adapter on the 10,003 training rows (§9).Satya
"Why is the baseline GPT-2 if it performs so badly?"Deliberately weak, to make the improvement visible and measurable. We also state its limit honestly: its 1,024-token context is shorter than our ~1,600-token few-shot prompt, so any GPT-2 few-shot number partly measures truncation, not capability (§13).Vishruth
"How do you know the few-shot examples didn't leak into evaluation?"Examples come only from the training split, and assert_no_overlap in the runner refuses to start if any example text is also an evaluation query. §7 states it; the preprocessing record logs the split sources.Vishruth
"Is the comparison statistically meaningful?"Paired on the same 385 messages, tested with exact McNemar: few-shot vs zero-shot p = 0.002, vs role/context p = 0.0002, vs constraint-based p = 0.002. The other three are indistinguishable (p 0.47–1.0), and we refuse to rank them.Satya
"Why two different GPUs?"A driver/CUDA mismatch: the newer torch build needed CUDA 13, which the server did not have. Both records are in Appendix F, within-experiment comparisons each come from one machine, and we rebuilt the evaluation sample on the second machine and confirmed it matched byte for byte.Vishruth
"What stops the model blocking someone's card wrongly?"block_card is never executed automatically — the router marks it as needing human confirmation, and our routing metric counts that withholding as correct, not as a miss. 14 of the 50 tool-triggering messages took that path.Kishore
"Your confidence value doesn't work. Why keep it?"Because reporting that it does not work is the honest result. It was effectively constant, so the 0.55 gate never fired; escalation is carried by the safety screen, failed validation, requires_human and the destructive-action rule instead. §11 and §13 both say so.Kishore

"Where is the structured-output schema?"Pydantic model in schema.py, printed as Appendix C, with validated samples in Appendix E. Five model-owned fields; anything extra, missing or mistyped is rejected.Kishore
