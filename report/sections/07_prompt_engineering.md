# 7. Prompt-engineering experiments

Requirement 11 asks for a reusable, parameterised prompt template. `prompts.build_prompt(strategy, query, allowed_intents, **kwargs)` is the single entry point the pipeline calls, so the whole of E2 is the same pipeline run four times with a different `strategy`; nothing else changes. All four strategies render the label catalogue, the tool catalogue and the output contract through the same three functions (`format_intent_catalogue`, `format_tool_catalogue`, `format_schema_contract`), and the contract is built from the pydantic model itself, so it cannot drift from the validator. A test asserts that these blocks are identical across the four prompts. That is what makes the comparison mean something: if each variant wrote its own schema text, a difference in accuracy could come from wording and not from the strategy. The full prompts, with the 77 labels, are in Appendix A.2.

Each strategy has a written reason for its design:

- **Zero-shot** gives the instruction, the catalogues and the output contract, and no examples. It is the floor: how much of the task an instruction-tuned model already understands from the label names and the schema alone. It is also the cheapest in prompt tokens, which matters because the 77-label catalogue already makes up most of the prompt.
- **Few-shot** [13] adds four worked query-to-JSON examples. We expect two separate effects, and the table lets us read them apart: the examples show the output format, which should raise schema validity, and they can disambiguate confusable intents, which should raise accuracy. The examples come from the **training split only**, picked by `data_prep.build_example_bank` to cover each routing outcome (a delivery lookup, a branch lookup, a destructive escalation and a text-only reply), with every evaluation text excluded. The runner refuses to start if any example is also an evaluation query. The bank holds one example from each side of the observed `card_arrival` / `card_not_working` confusion (§12.1), which is a direct test of whether worked examples fix it.
- **Role and context** gives the model the persona of a tier-1 support agent on a live-chat channel, and states the operating context: first-line triage, simulated systems, a human colleague always available, and no authority to resolve the account. It targets the quality and safety of the reply and the use of escalation, not label accuracy, so it is read against the response-safety rate and the `requires_human` rate as well as against accuracy.
- **Constraint-based** states hard output rules with a prohibition for each way the output can fail: exactly one JSON object and nothing around it (`no_json_found`), valid JSON syntax (`malformed_json`), exactly the five model-owned fields and no invented ones (`schema_violation`), and a label copied verbatim from the catalogue (`unknown_intent`). Its headline metric is validity on the **first** attempt, before the repair loop, because the aim is to rely on repair less.

**Protocol.** All four run the same 385 evaluation queries under greedy decoding with at most 192 new tokens, so the only thing that varies is the strategy. Each query goes through the unchanged pipeline: validation, up to two repair attempts, the confidence gate, tool routing and the safety screen. To fit a free T4, first-attempt prompts are generated in batches of 16 and replayed through the pipeline; repair prompts, which are rare, are generated one at a time, and the number of each is recorded. Qwen's chat template adds a default system prompt to every request (§4.2); it is the same for all four strategies, so the comparison stays fair, but it means the role-context persona sits in the user turn beneath that generic one.
