# 13. Limitations

**What the numbers can support.** Each E2 condition is a single run over 385 queries. At 50% accuracy that sample gives a 95% interval of about plus or minus five points, so a gap of two or three points between strategies is within noise and should not be read as a ranking. With five queries per intent, a per-intent result moves in steps of 20 points, so the confusion analysis points to patterns and does not measure them. The E3 subset has 77 queries, so one query is 1.3 points. The BANKING77 labels are also fine-grained and overlapping by construction, which caps the accuracy any system can reach on them.

**What the model reports.** `confidence` is a number the model writes, not a calibrated probability (§4.2). The escalation threshold of 0.55 acts on it, so the gate is only as trustworthy as the model's self-assessment, and we did not measure calibration. Output is validated after generation and repaired by asking again; it is not constrained during decoding, so a small model can still produce an invalid object or an invented label, which is why the repair loop and escalation exist.

**Prompts and models.** Qwen's chat template adds a default system prompt to every request, so the role-context persona sits in the user turn beneath a generic one. GPT-2's 1,024-token context is shorter than the roughly 1,600-token few-shot prompt, so any few-shot result for GPT-2 partly measures truncation and not capability. We used one instruction-tuned model of 1.5 billion parameters and did not compare model sizes, retrieval or fine-tuning (§9), and a larger model could change which strategy wins.

**Batching.** To fit a free T4, first-attempt prompts are generated in batches. Padding changes floating-point accumulation, so batched greedy output can very occasionally differ from unbatched output, and a sampled result depends on the batch it ran in. We fixed the batch size at 16 and stored it with every result, but we did not re-run the full sweep unbatched to measure the difference.

**Safety.** The reply screen is rule-based. It looks for a request cue next to a credential term and for stated account figures, so it will miss a reworded request and it can flag an innocent one. It stops the specific harm we observed (§12.1) and is not a general guarantee. The tools are simulated and conversations are single-turn, so we did not test multi-turn confirmation of a destructive action.

**Metrics need checking against intended behaviour.** The first version of the routing metric compared the expected tool with the tool that actually ran. The pipeline deliberately never auto-executes `block_card` and escalates instead, so a run with 100% intent accuracy scored 25% on routing, and on the full evaluation sample the metric could never have exceeded 70%. It was scoring a working safety control as a defect. Review caught it, and the fix reports correctly withheld calls in their own column. The lesson is general: any metric added later has to be tried against the destructive-refusal path first.
