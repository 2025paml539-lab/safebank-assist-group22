# 13. Limitations

**What the numbers can support.** Each E2 condition is one run over 385 queries. At 50% accuracy that gives a 95% interval of about plus or minus five points, so we rely on the paired tests in §7 and not on gaps of a few points. With five queries per intent a per-intent result moves in steps of 20 points, so the confusion analysis points to patterns and does not measure them, and one E3 query is 1.3 points. The BANKING77 labels are fine-grained and overlapping by construction, which caps the accuracy any system can reach on them. We used one 1.5-billion-parameter model and did not compare model sizes, retrieval or fine-tuning (§9).

**What the model reports.** `confidence` is a number the model writes, not a calibrated probability, and in practice it was constant: every valid few-shot reply said 0.9, so the 0.55 gate never fired and escalation rests on the safety screen, the validator and the destructive-action rule (§11). Output is validated after generation and not constrained during it, so a small model can still produce an invalid object or an invented label. Repair cannot rescue an invented label because its prompt does not list the valid labels (§10.1); we did not test a repair prompt that does.

**Prompts and models.** Qwen's chat template adds a default system prompt to every request, so the role persona sits in the user turn beneath a generic one. GPT-2's 1,024-token context is shorter than the roughly 1,600-token few-shot prompt, so any GPT-2 few-shot result partly measures truncation. E1 ran on a T4 and E2 to E6 on an A100 with different library versions (Appendix F), so comparisons hold within a setup and not across them.

**Batching.** To fit a free T4, first-attempt prompts are generated in batches. Padding changes floating-point accumulation, so batched greedy output can occasionally differ from unbatched output, and a sampled result depends on the batch it ran in. We fixed the batch size at 16 and stored it with every result. The same 77 greedy queries ran in two differently composed batches (E2 and E3) and 1 of 77 results changed, to another wrong label, so the effect looks small, but we did not re-run the sweep one query at a time.

**Safety.** The reply screen is rule-based. It looks for a request cue next to a credential term and for stated account figures, so it will miss a reworded request and it can flag an innocent one. It stops the specific harm we observed (§12.1) and is not a general guarantee. The tools are simulated and conversations are single-turn, so we did not test multi-turn confirmation of a destructive action.

**Our predictions.** Only 5 of the 181 wrong answers fell in the six confusable pairs we named before the run (§12.1), so the focus set is a lens on a few themes and not a map of where the system fails.

**Metrics need checking against intended behaviour.** The first version of the routing metric compared the expected tool with the tool that actually ran. The pipeline deliberately never auto-executes `block_card` and escalates instead, so a run with 100% intent accuracy scored 25% on routing, and on the full sample the metric could never have exceeded 70%. It was scoring a working safety control as a defect. Review caught it, and the fix reports correctly withheld calls in their own column. Any metric added later has to be tried against the destructive-refusal path first.
